# البنية المعمارية لمنصة InWork

## 1. تعريف المنتج وحدوده

InWork منصة خدمات تشاركية ذكية متعددة المجالات تربط طالبي الخدمات بمقدميها. لا تُبنى حول النقل أو تتبع المركبات، ولا تُقيد بمجال مهني أو مدينة واحدة. يمكن للخدمة أن تكون حضورية ضمن نطاق جغرافي أو عن بُعد.

## 2. الطبقات المعمارية

- **Presentation:** Next.js App Router وReact وTailwind CSS، مع العربية RTL افتراضيًا ودعم LTR.
- **Domain:** كتالوج المجالات، ملفات مقدمي الخدمة، الخدمات المعروضة، طلبات الخدمة، العروض، التقييمات.
- **Data:** Supabase PostgreSQL.
- **Identity:** Supabase Auth وربط كل سجل حساس بمعرّف المستخدم.
- **Authorization:** Row Level Security على كل جداول المجال، مع فصل صلاحيات العميل ومقدم الخدمة والإدارة.
- **Automation / Quality:** GitHub Actions لفحوص الاختبار وLint وBuild.

## 3. نموذج المجال

- `service_categories`: مجالات مرنة قابلة للإضافة والتعطيل.
- `provider_profiles`: الملف المهني العام لمقدم الخدمة، دون كشف بيانات اتصال خاصة في الاستعلام العام.
- `provider_services`: الخدمات الفعلية التي يقدمها كل ملف، مع نموذج التسعير.
- `service_requests`: احتياج العميل، ونطاق الخدمة، والميزانية الاختيارية، وحالة الطلب.
- `service_offers`: عروض مقدمي الخدمة المرتبطة بطلب محدد.
- `service_reviews`: تقييمات مرتبطة بطلب مكتمل.

توجد جداول `jobs` و`favorites` القديمة في المخطط السابق. هذه الهجرة إضافية ولا تحذفها أو تعيد تفسيرها؛ يجب عزل أي تدفقات توظيف متبقية أو ترحيلها بقرار مستقل بعد مراجعة البيانات.

## 4. قواعد المجال الأساسية

- لا يُنشأ عرض إلا من مقدم خدمة لديه ملف ظاهر وخدمة نشطة في مجال الطلب.
- لا يظهر ملف مقدم الخدمة للعامة إلا إذا كان ظاهرًا ومعتمد التوثيق من الإدارة.
- لا يُعرض الطلب المفتوح لمقدم خدمة إلا إذا كان لديه خدمة نشطة مطابقة للمجال وكان ملفه موثقًا وظاهرًا.
- لا يرى العميل عروض طلبه إلا صاحب الطلب، ولا يرى مقدم الخدمة إلا عروضه وطلبات المجالات المطابقة.
- لا يستطيع مقدم الخدمة اعتماد توثيقه بنفسه؛ تغيير `is_verified` محمي من جلسات المستخدم العادية.
- قبول العرض وتحديث حالة الطلب يجب أن يتمّا لاحقًا عبر عملية خادمية ذرية تتحقق من ملكية الطلب وحالة العرض وتمنع قبول أكثر من عرض.
- لا تمنح واجهة العميل أو مقدم الخدمة صلاحيات مباشرة لتغيير حالات الاعتماد أو التحقق.
- لا تُعرض التقييمات إلا وفق سجل خدمة مكتملة.

## 5. الموقع والخرائط

الموقع عامل اختياري حسب طبيعة الخدمة. يدعم النظام نطاقًا جغرافيًا نصيًا وخيار الخدمة عن بُعد في المرحلة الحالية. يمكن إضافة إحداثيات دقيقة أو خرائط Leaflet/OpenStreetMap عند الحاجة الفعلية، دون جعل الخريطة أو المسار محور المنتج.

## 6. المدفوعات

لا تُعتبر أي وسيلة دفع مفعّلة لمجرد ذكرها في الوثائق. يجب اعتماد مزود الدفع أو آلية التحصيل، والتحقق من المتطلبات القانونية والأمنية والتشغيلية، ثم تنفيذ تأكيد خادمي موثوق قبل تسجيل أي دفعة أو عمولة.

## 7. الأمان والخصوصية

- تفعيل RLS على جداول المجال الجديدة.
- عدم وضع مفاتيح الخدمة أو الأسرار في متغيرات NEXT_PUBLIC أو المتصفح.
- إبقاء عمليات القبول وتغيير الحالات والتحقق الإداري في طبقة خادمية موثوقة.
- التحقق من المدخلات في الخادم باستخدام Zod قبل الكتابة.
- عدم كشف الهاتف أو البريد أو بيانات الموقع الدقيقة في الملفات العامة.
- تسجيل الأحداث الإدارية الحساسة دون تخزين أسرار أو محتوى شخصي زائد.
- مراجعة سياسات RLS باختبارات سلبية وإيجابية قبل إطلاق الإنتاج.

## 8. حالة التنفيذ

المستودع يحتوي على واجهة تفاعلية أولية ومخطط SQL إضافي للخدمات التشاركية. ما زال يلزم تنفيذ وربط المصادقة وعمليات القراءة والكتابة الخادمية، القبول الذري للعروض، الرسائل، الإشعارات، التحقق الإداري، الدفع، ومراجعة سياسات RLS عمليًا قبل الإطلاق.
